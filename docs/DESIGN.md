# ADR: Wallet Engine

## Requirement analysis
- gRPC service: `Debit`, `Credit`, `GetBalance`
- `wallets` = wallet current-state projection
- `wallet_ledger` = transactions log; append-only, never updated or deleted
- per request, 2 separate operations:
  1. request processing + balance change — atomic, single DB transaction
  2. RabbitMQ event publishing — separate operation, broker failure must not fail request processing (DDD: command -> aggregate update -> domain event)
- transactions for a `wallet_id` are applied sequentially; different wallets may be processed in parallel
- no negative balance
- duplicate `transaction_id` returns the original result without re-executing the movement
- `WalletUpdatedEvent` published for downstream analytics/fraud

## Assumptions
For simplification assume that:
- no currency
- all amounts are integers (`bigint`)
- request amounts are positive; direction comes from the RPC (Debit negates)
- stored movements are signed: Credit = positive, Debit = negative
- one request affects exactly one wallet; no wallet-to-wallet transfers
- `wallet_id` / `transaction_id` are UUIDs supplied by the caller; idempotency scope for `transaction_id` is global
- wallet must exist before Debit/Credit/GetBalance (created via `CreateWallet` or seed); no implicit creation
- only successful movements are written to the transactions log; rejected requests are not recorded
- transactions are all-or-nothing; no partial amounts
- no refunds, reversals, chargebacks, fees or limits
- no authentication/authorization (prototype, callers are trusted)
- timestamps are UTC and generated by the database
- `GetBalance` reads committed state only
- wallets are never deleted
- single Postgres + Redis + RabbitMQ per environment; no sharding
- no SLA/performance targets (prototype)

## Stack
- Java 21, Maven, Spring Boot 4.1.1
- gRPC: `spring-boot-starter-grpc-server` (Netty, port 9090)
- DB: PostgreSQL 17, Flyway migrations, Spring Data JPA
- Redis 8: distributed lock, Spring Data Redis (Lettuce)
- RabbitMQ 4: `spring-boot-starter-amqp`, publisher confirms enabled
- local infra: [compose.yaml](../compose.yaml) (Postgres + Redis + RabbitMQ)

## Data model
- Flyway owns the schema: [V1__wallet_schema.sql](../src/main/resources/db/migration/V1__wallet_schema.sql)
- `wallets(wallet_id uuid PK, amount bigint not null default 0, updated_at timestamptz not null)` — current-state projection
- `wallet_ledger(transaction_id uuid PK, wallet_id uuid FK, amount bigint not null, updated_at timestamptz not null)` — transactions log
- append-only enforced by trigger `trg_wallet_ledger_immutable` (UPDATE/DELETE rejected)
- `amount` is signed: positive = deposit (Credit), negative = withdrawal (Debit)
- `transaction_id` PK = one ledger row per request
- new migration for the background publisher: `publisher_state(last_processed_at timestamptz, last_transaction_id uuid)`

## Request processing
Debit / Credit:
1. acquire Redis distributed lock for `wallet_id`: `SET wallet:{wallet_id} NX PX <ttl>`; release: `DEL wallet:{wallet_id}`
2. `SELECT * FROM wallet_ledger WHERE transaction_id = ?`
   - found -> release lock, return the stored result
3. otherwise, one DB transaction:
   - `UPDATE wallets SET amount = amount + :amount, updated_at = now() WHERE wallet_id = :wallet_id AND amount + :amount >= 0`
   - 0 rows -> wallet not found: `NOT_FOUND`; balance would go negative: `FAILED_PRECONDITION`; no ledger row
   - `INSERT INTO wallet_ledger (transaction_id, wallet_id, amount)`
4. release lock, return new amount

- concurrent duplicates: second `INSERT` fails on the `transaction_id` PK -> rollback -> re-read the ledger row -> return the stored result

GetBalance:
- `SELECT amount FROM wallets WHERE wallet_id = ?`; no lock; not found -> `NOT_FOUND`

## Locking
To guarantee correct balance, all transactions must be applied to account sequentially, skipping transactions that will make account negative. Lock for `wallet_id` during transaction processing; different wallets must not block each other.

0. use queue per `wallet_id` so all requests for same wallet will be ordered and processed sequentially
- PROS:
    - no locking, just sequential request processing for same wallet
- CONS:
    - requires complicated request routing
    - will need more manual implementation

1. optimistic lock around `wallets` + retry
- PROS: fail fast approach, no lock wait
- CONS: need to implement "retry" mechanism, that increases complexity

2. pessimistic lock around `wallet_id`
- PROS:
    - introduce natural processing delay
    - simple to implement
    - no additional infrastructure required
- CONS:
    - will consume db connection and increase transaction time

3. use Redis for distributed lock
- PROS:
    - no db lock, smaller transaction time
- CONS:
    - Redis requirement — increase infrastructure complexity

Resolution:
- primary: 3 (Redis distributed lock)
- 2 (pessimistic lock around `wallet_id`) may be used instead — check Redis vs DB lock performance
- conditional `UPDATE` is the invariant in both cases: balance never goes negative even if a lock is skipped or expires
- lock TTL above max transaction processing time; lock acquisition timeout -> `ABORTED` (retryable)

## Event publishing
- background service, separate from request processing
- loop: read N new transactions from `wallet_ledger` since last processed timestamp, ordered by `(updated_at, transaction_id)`
- publish one `WalletUpdatedEvent` per transaction: `{ transaction_id, wallet_id, amount, updated_at }`; exchange `wallet.events`, routing key `wallet.updated`
- read N -> repeat; read < N -> sleep
- update last processed timestamp (DB + Redis) after publishing
- multiple nodes: Redis lock, so only one publisher runs at a time
- RabbitMQ down: retry with backoff; request processing is already committed and unaffected
- consumers dedupe by `transaction_id`

## Create wallet API
- `CreateWallet(CreateWalletRequest{wallet_id}) -> WalletResponse{wallet_id, amount, updated_at}`
- inserts `wallets(wallet_id, amount = 0)`; funding goes through `Credit`
- wallet already exists -> `ALREADY_EXISTS`
- Debit/Credit/GetBalance on unknown wallet -> `NOT_FOUND`, no implicit creation

## Error mapping
- `NOT_FOUND` — unknown wallet
- `ALREADY_EXISTS` — wallet already exists
- `FAILED_PRECONDITION` — balance would go negative
- `INVALID_ARGUMENT` — malformed request
- `ABORTED` — lock acquisition timeout, retryable
